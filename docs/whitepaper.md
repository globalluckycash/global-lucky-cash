## 1. 摘要

Global Lucky Cash 是一個完全建構在 Bitcoin Cash 鏈上的去中心化樂透遊戲。系統的每一分資金、每一條規則、每一次開獎，都以鏈上智能合約（CashScript）與原生 Token（CashTokens NFT）表達與強制執行，不存在任何中心化資料庫或後台帳本。玩家選號購票、開獎、驗證中獎、逾期處理、領獎等**每一個環節都是任何人皆可觸發的公開交易**——包括平台自己，在鏈上都不具備特殊權限。

系統的核心設計理念可以歸納為一句話：**規則寫死在合約裡，資金鎖死在合約地址裡，開獎結果由公開可驗證的預言機簽名決定，任何人都能推動流程、也都能驗證結果，平台只收取約定比例的手續費，不能拿玩家的錢、不能改規則、也不能讓遊戲停下來。**

除了給玩家一個公平透明的樂透選擇，Global Lucky Cash 也是為了替 Bitcoin Cash 網路貢獻真實交易量而存在：隨著區塊獎勵長期遞減，礦工的收入來源勢必要逐漸從區塊獎勵轉移到交易手續費，鏈上應用持續產生的交易量正是支撐這個轉型的關鍵。樂透這類高頻、小額、可重複觸發的交易場景，天然適合為 BCH 網路貢獻穩定的手續費收入——這是本系統存在的另一層動機。

- 號碼空間：32 選 3（普通號）× 16 選 1（特別號）= **79,360** 種組合
- 開獎週期：固定 3.5 天一輪（一週兩次）
- 獎金分配：每輪售票收入 **50% 進頭獎池 / 30% 進固定獎池 / 20% 歸平台**
- 隨機數來源：[oracles.cash](https://oracles.cash/api-docs/) 價格預言機的簽名訊息
- 支援無錢包購票：讓交易所提幣即可買票的消費者，無需先學會使用鏈上錢包

## 2. 問題：傳統樂透與現有鏈上博彩的信任缺口

傳統樂透系統的公正性建立在對發行機構的信任之上：

- **開獎過程不透明**：搖球機、電腦亂數產生器等機制由發行方單方面操作，玩家無法獨立驗證開獎結果是否真的隨機、是否被操縱。
- **資金去向不透明**：獎金池、營運費用實際去向鎖在發行方的私有帳本裡，外部只能看到官方公告的彙總數字。
- **規則可被片面更動**：抽成比例、獎項結構、開獎頻率等規則，理論上發行方隨時可以調整，玩家沒有事前的技術性保證。
- **跨境參與門檻高**：需要當地銀行帳戶、身分認證、實體通路，海外玩家難以公平參與。

即使是許多「鏈上博彩」專案，也只是把介面搬到區塊鏈上，實際的號碼產生、資金保管仍由中心化伺服器或多簽密鑰控制，玩家依然只能「相信」營運方沒有作弊——這與傳統模式並無本質差異。

Global Lucky Cash 嘗試從架構層面解決這個問題：**不是把信任從一個機構轉移到另一個機構，而是讓整個流程不再需要信任任何單一參與方**（隨機數來源除外，見第 9 節的誠實揭露）。

## 3. 解決方案概覽

Global Lucky Cash 的做法是：把樂透系統需要的**每一項狀態**（目前輪次、售票匯率、每個號碼賣出幾張票、開獎結果、獎池餘額……）都編碼成鏈上 UTXO 上的 CashTokens NFT，並用 CashScript 合約規則規定這些 UTXO 只能按照系統設計的方式被消費與重建。

這帶來幾個直接後果：

- **沒有後台資料庫**：所有狀態都在鏈上，任何人用區塊鏈瀏覽器或自己的節點就能查證。
- **沒有管理員開關**：合約一旦部署，鎖定邏輯就固定了；平台唯一保留的權限是對自己應得的營運分潤執行提領（`adminWithdraw()`），無法動用玩家資金或獎池。
- **流程由經濟誘因驅動，而非仰賴平台維運**：結算、彙整、進入開獎階段、開獎、驗證中獎等交易都設計了「執行獎勵」，任何人（包含玩家自己寫的腳本、第三方 keeper）執行這些交易都能拿到約定的獎勵，使系統即使平台伺服器故障也能持續運作。
- **開獎結果可獨立重算**：任何人都能拿公開的預言機歷史訊息，自行重算出與合約相同的中獎號碼，不需要相信平台的公告。

## 4. 為什麼選擇 Bitcoin Cash

樂透這類應用對底層鏈有幾個特別的要求，這些是選擇 BCH + CashTokens + CashScript 的具體理由：

| 需求 | BCH 提供的能力 |
|---|---|
| **原生 Token / NFT，不需額外的代幣標準合約** | CashTokens 是 BCH 協定層原生支援的同質化代幣與 NFT，鑄造（`minting`）、變更（`mutable`）、鎖定（`none`）等能力（capability）由協定本身保證，不需要像其他鏈一樣另外部署一份 ERC-721 風格的合約來實作代幣邏輯本身的安全性 |
| **UTXO 可以「攜帶狀態」並用合約規則保護** | CashScript 編譯出的合約地址支援 introspection（讀取 `tx.inputs[i]` / `tx.outputs[i]` 的內容），讓一張 UTXO 上的 NFT commitment 變成可驗證、可強制轉換規則的狀態容器——這是本系統把「輪次」「售出票數」「開獎結果」都做成 NFT 的技術基礎 |
| **高頻小額交易的可行性** | 樂透需要頻繁的小額售票交易與獎金分配，BCH 手續費低且確認快，適合這種交易密度 |
| **鏈上可驗證的價格預言機生態（oracles.cash）** | BCH 生態已有標準化、簽章可驗證的預言機訊息格式（見第 9 節），可直接作為隨機數熵源，不需要另外整合 Chainlink VRF 這類外部隨機數服務 |
| **平行處理高併發的空間** | 79,360 種號碼組合與高併發購票需求，透過「同一合約地址、多個 UTXO 各自靠 commitment 區分身份」的設計平行處理（見第 7 節），這是 UTXO 模型（相對於帳戶模型）的天然優勢——不同號碼的 UTXO 互不衝突，可以在同一時間被不同交易消費 |

## 5. 名詞解釋（BCH / CashTokens 基礎概念）

為了讓熟悉其他公鏈（例如 Ethereum）但不熟悉 BCH 特有模型的讀者能順利閱讀後續章節，先說明幾個關鍵詞：

| 名詞 | 說明 |
|---|---|
| **UTXO** | Unspent Transaction Output，未花費交易輸出。BCH 沿用比特幣的帳本模型：資產以一筆一筆獨立的「輸出」存在，花費時整筆消耗、重新產生新的輸出，與 Ethereum 的帳戶餘額模型不同 |
| **CashTokens** | BCH 2023 年上線的原生代幣標準，讓一個 UTXO 除了攜帶 BCH 金額外，還能攜帶一個 Token Category（代幣種類 ID）與一段任意資料（**NFT commitment**） |
| **NFT commitment** | 附加在一個 CashTokens NFT 上的任意長度資料欄位，相當於「這張 NFT 目前狀態的內容」。本系統用 commitment 儲存輪次、號碼、售出張數、獎池餘額等所有系統狀態 |
| **Capability（能力）** | CashTokens NFT 的三種模式：`none`（commitment 與存在性都不可變，如已售出的彩票憑證）、`mutable`（commitment 可修改，但不可再鑄造新 NFT）、`minting`（commitment 可修改，且可以在同一筆交易中鑄造新的同類 NFT）。系統藉由選擇正確的 capability，精準控制哪些狀態可以被改變、哪些不行 |
| **Covenant（合約限制）** | CashScript 合約透過檢查交易本身的輸入輸出內容（*introspection*），限制一個 UTXO 只能被以特定方式消費並重建，是「規則寫死在合約裡」的實作手段 |
| **Dust** | 一個 UTXO 為了維持有效性必須保留的最低 BCH 金額，本系統統一取 1,000 satoshi |
| **Oracle（預言機）** | 把鏈下資訊（例如 BCH/USD 匯率）以簽章方式帶入鏈上供合約驗證的服務。本系統使用其簽章訊息同時做為「不可預測隨機數」的熵源（見第 9 節） |

## 6. 遊戲規則與獎項設計

### 6.1 選號規則

- **普通號**：1–32 選 3
- **特別號**：1–16 選 1
- **號碼組合總數**：C(32,3) × 16 = 4,960 × 16 = **79,360 組**
- **票價**：每組號碼為固定的 USD 等值 BCH（依當輪售票匯率換算，匯率與票價分離，票價由合約 constructor 參數 `ticketPriceCents` 決定）；設計值為 1 USD，開發、測試、正式環境目前皆採此值
- 單筆交易可一次購買 **1 至 10 組**不同號碼，每組各自鑄造一張彩票憑證（TicketNFT）

### 6.2 獎項設計

| 中獎條件 | 獎金 | 中獎機率（約） |
|---|---|---|
| **頭獎**：3 個普通號全中 + 特別號全中 | 按持票比例均分當期「總頭獎池」全部餘額（非固定金額） | 1 / 79,360 |
| 僅中 1 特別號（不含普通號） | 2 倍票價 | 1 / 21.7 |
| 1 普通號 + 1 特別號 | 5 倍票價 | 1 / 65 |
| 2 普通號 + 1 特別號 | 20 倍票價 | 1 / 912 |
| 3 普通號（不含特別號） | 100 倍票價 | 1 / 5,291 |

固定獎項整體中獎率約 **1/15.9**（任一等級）。固定獎池每張票收入 0.3 USD，期望支出約 0.21 USD/張，保留約 30% 安全邊際，確保長期資金充足。

頭獎池則採「按輪累加、有人中獎才清空」的模式：若連續多輪無人中頭獎，頭獎池會持續累積、金額越滾越大，直到有玩家湊齊全部號碼為止——這與大眾熟悉的「累積獎金型」樂透機制一致，但獎池餘額與中獎判定完全由鏈上合約即時執行，任何人隨時可查詢當前頭獎池的實際 BCH 餘額。

## 7. 系統架構：狀態即 UTXO

Global Lucky Cash 沒有任何鏈下資料庫。系統運作所需的一切狀態，都表達為特定 Token Category 下、不同用途碼（purpose byte）的 NFT，鎖定在各自的 CashScript 合約地址上。下表是完整清單：

| 用途碼 | NFT 名稱 | 數量 | Capability | 作用 |
|---|---|---|---|---|
| `01` | **RoundShardAuthNFT**（輪次分片授權票） | 64 個 | `minting` | 提供當下正確輪次資訊；分 64 片平行承接售票流量，玩家付款 BCH 暫存於此 |
| `02` | **NumberSalesNFT**（號碼售出計數票） | 79,360 個 | `mutable` | 每個號碼組合各一個 UTXO，記錄該號碼賣出幾張票，用於計算頭獎應分幾份 |
| `03` | **RoundSwitchControlNFT**（換輪管控票） | 全系統唯一 1 個 | `minting` | 彙整 64 個分片的結算進度，記錄目前輪次、截止售票時間、累積售出票數 |
| `04` | **DrawingNFT**（開獎用票） | 每輪 1 個（用後銷毀） | `minting` | 記錄本輪開獎期號與預計開獎時間，防止重複開獎 |
| `05` | **WinningNumberNFT**（中獎號碼票） | 每輪 2 個 | 固定獎池端 `minting`；頭獎池端 `none` | 記錄本輪中獎號碼；一份永久留在固定獎池供玩家隨時領固定獎，一份送到頭獎池驗證後銷毀 |
| `06` | **ConfigNFT**（設定票） | 全系統唯一 1 個 | `none` | 記錄創世時間、每輪長度、分片數量等固定參數，供換輪相關交易讀取比對 |
| `07` | **CanceledRoundNFT**（取消輪次票） | 每次取消開獎產生 1 個 | `minting` | 預言機故障逾時未能開獎時鑄造，作為玩家憑此拿回本輪票款的憑證（見第 10 節） |
| `08` | **DonationMessageNFT**（贊助留言票） | 每次贊助回收產生 1 個，永久保留 | `none` | 記錄某次頭獎贊助的輪次、金額與留言雜湊，作為公開可查的贊助紀錄 |
| `09` | **ShardSettlementNFT**（分片結算票） | 每片每輪 1 個 | `mutable` | `settle()` 產生，暫存單一分片結算後、尚未彙整進總控 NFT 的售票金額與張數（見第 8 節） |
| `0A` | **JackpotPoolNFT**（頭獎池狀態票） | 隨中獎次數遞增 | `minting` | UTXO 本身持有全部頭獎 BCH；記錄目前是「累積中」或「已中獎待領」 |
| `0B` | **GameOverNFT**（遊戲結束確認票） | 全系統唯一 1 個（僅於遊戲永久結束時鑄造） | `none` | 記錄遊戲正式宣告結束的時間，作為各合約 `endGame()` 收尾函式的觸發憑證（見第 10 節） |
| `0C` | **JackpotClaimRangeNFT** | 遊戲結束收尾時產生 | `none` | 供玩家在遊戲結束後，憑此依比例領回尚未派發的頭獎分潤 |
| — | **TicketNFT**（彩票憑證） | 每次購票鑄造 | `none` | 玩家持有的中獎憑證，鎖定於玩家自己的錢包地址，沒有獨立合約 |

平台池與固定獎池則刻意**不使用任何 NFT**，只以純 BCH（無 token）停放在各自的合約地址：資金由多筆 UTXO 共用同一地址持有，平台池僅支援 `adminWithdraw()` 由平台提領營運分潤，固定獎池的領獎邏輯則由上述 WinningNumberNFT（`minting`）驅動。

**為什麼要切成 64 片 / 79,360 個 UTXO？** 因為 UTXO 模型下，同一個 UTXO 在同一時間只能被一筆交易消費。如果全系統只有一個「售票總帳」UTXO，所有玩家的購票交易就會互相搶佔、大量失敗。透過把「輪次授權」切成 64 個分片、把「號碼銷售計數」拆成 79,360 個各自獨立的 UTXO，不同玩家買不同號碼、甚至買同一號碼但用不同分片的交易可以同時上鏈，天然達到水平擴展。64 這個片數之所以夠用，是因為 BCH 支援未確認交易（0-conf）無限接續——同一分片內的多筆購票交易不需要等前一筆先確認上鏈，可以連續串接送出，不需要靠大量分片數量才能撐住高併發，64 片已足以提供充分的平行處理空間。

**每個合約如何辨識一堆共用同一地址的 UTXO 屬於誰？** 靠 NFT commitment 裡的欄位區分：RoundShardAuthNFT 用「分片編號」（0–63），NumberSalesNFT 用「樂透號碼」（4 bytes 編碼）。合約在驗證交易時會對每一筆 NFT 輸入做**三重驗證**——Token Category 是否正確、commitment 長度是否正確、用途碼是否正確——避免有心人士構造出格式相符但內容偽造的 NFT 混入交易而被誤判。

以彩票憑證 TicketNFT 為例，其 commitment 直接以十六進位方式編碼、方便玩家肉眼核對：

```
0003ff01020304ff00000080ff00
```

依序代表：第 3 輪、普通號 1/2/3、特別號 4、售票匯率 128、領獎狀態「未兌獎」。玩家不需要依賴前端介面的解讀，理論上可以直接讀懂自己持有的憑證內容。

## 8. 輪次生命週期與資金流

### 8.1 六個階段，任何人都可觸發

![六個階段狀態圖：售票中→結算中→彙整中→待開獎→已開獎](/whitepaper/round-lifecycle-zh.png)

新一輪的售票在「進入開獎階段」交易完成、輪次號碼遞增的當下就立刻可以開始，不需要等待上一輪的開獎與領獎跑完——售票、結算、彙整、開獎、驗證中獎、頭獎與固定獎的領獎，彼此重疊並行，互不阻塞。

「結算」與「彙整」是兩種不同的交易：每個分片的售票截止時間各自獨立，時間一到，任何人就可以對**那一片**發起 `settle()`，把該分片累積的售票金額從 RoundShardAuthNFT 轉入一張 ShardSettlementNFT，此時金額仍分散在各分片、尚未彙整。等到全部分片都完成結算，才由 `aggregate()` 把這些分散的 ShardSettlementNFT 彙整進總控的 RoundSwitchControlNFT——由於單筆交易的大小上限，彙整固定分兩批，每批處理 32 片，兩批都完成才代表本輪彙整完畢，才能進入開獎階段。

### 8.2 資金流：50/30/20 的分配時機與比例

玩家付款的 BCH 並不會在售票當下就即時拆分進各個獎池，而是先暫存、待「進入開獎階段」交易時一次性依比例分配，路徑如下：

```
玩家購票付款
   → 暫存於 RoundShardAuthNFT（售票期間持續累加，逐分片各自獨立）
      → settle()：該分片結算，金額轉入 ShardSettlementNFT（仍分散於各分片）
         → aggregate()：分 2 批、每批 32 片，彙整進 RoundSwitchControlNFT
            → 進入開獎階段交易時，依固定比例一次分配：
                50% → 頭獎池（JackpotPoolNFT，直接累加 BCH 餘額）
                30% → 固定獎池（純 BCH，供 4 級固定獎支出）
                20% → 平台（純 BCH，供平台提領營運費用）
```

這個設計把「頻繁的小額售票」與「低頻的大額分配」分開處理：售票交易不需要每筆都拆成三份輸出付給三個獎池，只需把錢原封不動地滾存到下一站，直到彙整完成的那一刻才真正做一次性分配，降低整體手續費與合約複雜度。

### 8.3 經濟誘因：讓系統不需要仰賴平台維運

結算、彙整、進入開獎階段、開獎、驗證中獎、逾期處理這幾種「推進系統」的交易，都內建了**固定等值 1 USD 的執行獎勵**（逾期處理則另外提撥逾期獎金的 1%），由觸發交易的人取得。也就是說：

- 任何人（包含玩家自己，或第三方 keeper 服務）都可以寫一個腳本，持續監控鏈上狀態，一旦條件成立就搶著送出交易賺取執行獎勵。
- 這讓系統的「心跳」不依賴平台伺服器 24 小時運作——即使平台的維運服務全部停機，只要還有任何一方（甚至只是想賺獎勵的路人）願意執行，遊戲流程就會持續推進。
- DrawingNFT 在「進入開獎階段」交易鑄造時，會額外攜帶約 3 USD 等值的準備金，供後續「開獎」「驗證中獎」兩筆交易各自支付執行獎勵，確保獎勵資金來源穩定、不因票量不足而歸零。

### 8.4 頭獎領獎範例

頭獎採「按目前持票比例逐一領獎」的方式結算，而非一次性平分給所有中獎者。以下是一個簡化範例（忽略 dust 扣除項）：

> 頭獎池累積 300 BCH，共有 3 張中獎彩票尚未領獎。
> 第一位領獎者領走 300 ÷ 3 = 100 BCH，池子剩 200 BCH，剩餘可領人數變為 2。
> 第二位領獎者領走 200 ÷ 2 = 100 BCH，池子剩 100 BCH，剩餘可領人數變為 1。
> 第三位領獎者領走 100 ÷ 1 = 100 BCH，池子降至僅剩 1,000 sats dust。

每一位中獎者最終都領到等額的 100 BCH，計算方式確保無論領獎順序如何，也無論領獎期間池子餘額如何變動，每個人都能領到公平的一份。

## 9. 隨機性與可驗證公正性

樂透系統的核心信任問題在於「開獎號碼從哪裡來」。Global Lucky Cash 採用 [oracles.cash](https://oracles.cash/api-docs/) 標準的價格預言機簽名訊息作為隨機數熵源，具體流程：

1. 合約在部署時就寫死一組**預言機公鑰**（目前由 General Protocols 營運），只接受這把公鑰簽署的訊息。
2. 開獎交易需要提供**兩筆連續**的預言機報價（Message Sequence 必須恰好相差 1），且第一筆的時間戳記早於預計開獎時間、第二筆的時間戳記晚於或等於預計開獎時間。
3. 以**第二筆報價的簽名**做 `sha256(signature) mod 79,360`，推導出中獎的號碼組合索引。
4. 該索引再依固定公式反推回具體號碼組合：`idx = comboIdx × 16 + (特別號 − 1)`，其中 `comboIdx` 由普通號 3 → 普通號 2 → 普通號 1 的巢狀枚舉順序決定，特別號則是最內層、變化最快的部分。

### 9.1 為什麼觸發者無法挑選對自己有利的報價

預言機的訊息序號（Message Sequence）全域嚴格遞增、時間戳記單調遞增，因此「第一筆時間戳早於預計開獎時間、第二筆時間戳晚於或等於預計開獎時間」且序號相鄰的報價組合，在整個預言機歷史中是**唯一**的一組，任何人都可以自行下載公開的預言機歷史訊息重算驗證——這代表**任何第三方都能獨立覆核每一輪的開獎結果是否正確**，不需要相信平台的一面之詞。這也是本系統前台已提供「公開驗證」頁面的原因。

### 9.2 誠實揭露的信任假設

作為一份誠實的白皮書，我們必須指出：目前系統仰賴**單一預言機營運方**（General Protocols）的簽名公鑰作為隨機數來源，本質上仍存在一個中心化的信任點——若該預言機停止服務或私鑰外洩，會直接影響開獎流程的可用性與安全性。這與「完全去信任（trustless）」的理想狀態之間仍有落差，是本系統目前唯一保留的外部信任假設。預言機故障導致無法開獎時的退款機制已經實作（見第 10 節），其餘相關風險揭露詳見第 15 節。

具體來說，私鑰外洩的後果不只是「影響開獎流程」這麼抽象：第 9.1 節「報價組合全域唯一」的保證，前提是報價確實來自預言機的真實歷史紀錄；一旦私鑰外洩，攻擊者不再受這份歷史紀錄限制，可自行捏造一筆從未發生過的報價（匯率、時間戳、序號皆可自訂）並用外洩的私鑰簽名，合約僅驗證簽章是否對應這把公鑰，無法分辨報價真偽。也就是說，私鑰外洩不是「提高被預測的機率」，而是讓持有私鑰的人可以直接指定中獎號碼。每一輪開獎後，任何人仍可拿 WinningNumberNFT 記錄的報價時間，回頭比對 oracles.cash 的公開歷史是否吻合，藉此事後抓出偽造的報價——但這僅是事後稽核，無法在資金被領走前先行阻止。

## 10. 安全設計與威脅模型

系統設計過程中，針對以下攻擊面做了具體分析與處置：

| 風險 | 處置狀態 | 說明 |
|---|---|---|
| 重複領獎 / 偽造彩票憑證 | **已解決** | CashTokens 協定層保證 Token Category 無法偽造；彩票憑證的「領獎狀態」欄位由合約強制寫入，已領獎的憑證無法再次使用 |
| 預言機隨機數操縱（觸發者挑報價） | **已解決** | 如第 9.1 節所述，符合條件的報價組合在預言機歷史中全域唯一，觸發者無從選擇對自己有利的組合；此保證以預言機私鑰未外洩為前提，私鑰外洩後的風險與因應見第 9.2 節 |
| 結算 / 彙整交易被重複觸發 | **已解決** | `settle()` 驗證分片自己的輪次須與該片產生的 ShardSettlementNFT 一致，`aggregate()` 另外驗證 ShardSettlementNFT 輪次須與總控 NFT 一致；結算或彙整完成後，各自的條件即不再成立，無法重複執行 |
| 獎金 / 憑證被導向錯誤地址 | **已解決** | 所有鑄造 NFT 與支付獎金的輸出，合約層強制驗證 `lockingBytecode` 必須等於玩家付款輸入或持有憑證的地址，杜絕交易建構者將資產導向自己或第三方地址 |
| NFT 輸入偽造注入 | **已解決** | 每筆 NFT 輸入均須通過 Token Category、commitment 長度、用途碼三重驗證，防止同一 Token Category 下不同角色的 NFT 被混用誤導合約邏輯 |
| 固定獎池短時間內餘額不足 | **已知邊界，初期接受** | 固定獎沒有領獎期限，玩家可待下一輪資金挹注後重試；不影響本金安全 |
| 系統推進停滯 | **已知邊界，初期接受** | 由於第 8.3 節的執行獎勵機制對所有參與者皆有利，實務上發生「無人願意推進」的機率極低 |
| 預言機長期故障導致無法開獎 | **已解決** | 預計開獎時間過後 2 小時內仍無法取得有效預言機報價時，任何人都可以觸發 `cancelDraw()` 取消本輪開獎，鑄造 CanceledRoundNFT；玩家憑此透過 `claimCanceledRoundRefund()` 拿回本輪已付的票款 |
| 換輪延遲攻擊（cutoffTime 操縱） | **已解決** | 「預計開獎時間」並非取決於觸發者實際送出結算/彙整交易的時間，而是取自 64 個分片各自的 `lastSoldTime` 棘輪（每次售票都會寫入、單調不減、跨輪不歸零）彙整後的最大值再加 3 小時（`aggregate()` 計算 `maxLastSoldTime`，`enterDrawingPhase()` 據此算出 `expectedDrawTime`）。觸發者若想刻意延後、把預計開獎時間喬到已公開的預言機歷史時間點，必須讓全部 64 個分片在同一段時間內都沒有任何一筆真實售票——只要售票期間有任何一位誠實玩家在任一分片買票，該分片的 `lastSoldTime` 就會貼近實際時間，使最大值貼近真實時間，攻擊者無從操控 |

**「已解決」的具體意義**：上述標記為已解決的項目，代表現有合約邏輯已完整覆蓋，不依賴審計或後續補強；標記為「已知邊界」則是團隊評估後認為可以接受的限制，不影響玩家本金安全。

**關於合約升級與漏洞修補**：本系統採用完全去中心化的合約架構，資金鎖定在公開可查的合約地址，規則寫死且無法片面調整。這個設計必然帶來一個取捨：若要保留「發現漏洞後可修補」的能力，勢必需要某種鏈上權限可以把尚在累積中的頭獎獎池等資金搬移到新合約，而這樣的權限一旦存在，玩家就必須信任平台不會濫用它——這正是本系統從一開始就要避免的信任缺口（見第 2 節）。

因此，遊戲正式上線後，平台**不會保留、也不會設計任何形式的合約升級或漏洞修補機制**。若上線後合約邏輯被發現存在漏洞並造成資金損失，平台無法對此進行賠償，也不會透過任何方式在原合約上「打補丁」或搬移資金——這是選擇完全去中心化、拒絕平台特殊權限所必然伴隨的風險，由玩家與平台共同接受。

**遊戲永久結束後的收尾清算機制**：8 份合約都各自實作了一個由 Admin 授權 NFT 觸發的 `endGame()` 函式，但這**不是**上述「升級 / 修補」的例外——它只有在遊戲已經**永久結束**（連續 4 輪開獎因預言機故障被取消，觸發 `declareGameOver()` 正式宣告遊戲結束）之後才可能被呼叫，且針對頭獎池與固定獎池這兩個實際持有玩家資金的合約，還額外要求宣告結束後再等待 **90 天**，讓玩家有充分時間先透過 `claimJackpotShareRefund()` 領回自己依比例應得的頭獎分潤，才輪到 `endGame()` 把等待期滿後仍無人領取的殘餘資金做最終清算。也就是說，這是「遊戲確定不會再有下一輪、玩家都已有機會領回自己那份之後」的退場清算，而不是遊戲進行中可以隨時介入、搬動資金的權限。

## 11. 無錢包購票：降低參與門檻

考量到多數樂透玩家並不熟悉加密貨幣錢包的操作，系統設計了 **TicketDeposit** 機制，讓玩家不需要先學會使用鏈上錢包也能參與：

1. 平台依玩家選定的輪次與號碼組合，計算出一個**唯一、確定性**的一次性合約地址。
2. 玩家只需要從任何來源（例如交易所提領）把足額 BCH 匯到這個地址，不需要簽署任何鏈上交易。
3. 平台監控到入帳後，代為送出購票交易，彩票憑證會**直接**鑄造到玩家指定的收款地址，無需二次轉交。
4. 若因輪次已切換等原因導致購票無法執行，**任何人**都可以呼叫退款函式，把 BCH 強制退回玩家地址——包含平台自己都無法把這筆錢佔為己有或導向別處。

這個設計把「先買 BCH、再學錢包、再操作合約」的三道門檻，簡化成「把錢匯到一個地址」，同時仍然保留「玩家資產只能回到玩家自己手上」的鏈上強制保證。
